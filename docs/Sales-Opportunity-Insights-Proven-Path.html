Source of truth

One bundle, everything included

The whole app lives in a single AppFrameworkTemplateBundle in git: 10 CSVs, 10 data-stream definitions, the semantic model, 15 visualizations, the dashboard, and a 48-node create chain that builds them in order. The two rules that make it portable: it ships its own data, and every cross-asset reference is a ${App...} token instead of an org-specific name.

Packaging

2GP was dead — the classic door was open

Modern packaging (sf package version create) needs the Package2 object, which our publisher org never provisioned despite every toggle showing Enabled. The bypass: first-generation Package Manager, which has shipped install URLs for a decade and needs none of it. The unlock was discovering the component picker calls the bundle type "App Template" and the logo image "Asset File".

# Setup → Package Manager → New (Unmanaged) → Add:
Component Type "App Template"  →  Sales_Opportunity_Data
Component Type "Asset File"    →  APEX_essential_components
# → Upload → version name → the page prints the Installation URL.

The 2GP dead end — orgfarm never provisioned Package2 despite both toggles Enabled. Verbatim probe transcript, 40+ minutes after enablement.

$ sf data query -q "SELECT COUNT() FROM Package2" -o tbxfarm
ERROR at Row:1:Column:22
sObject type 'Package2' is not supported.

$ sf data query -q "SELECT QualifiedApiName FROM EntityDefinition
    WHERE QualifiedApiName IN ('Package2','Package2Version')" -o tbxfarm
[]           <- not even in the org's schema dictionary

# yet the org SAYS it is a Dev Hub:
$ sf org list limits -o tbxfarm | grep -E "Scratch|Package"
  ActiveScratchOrgs                 3 / 3
  DailyScratchOrgs                  6 / 6
  Package2VersionCreates            6 / 6

# and the user HAS the permission:
$ ... PermissionSet WHERE PermissionsPackaging2 = true
  1 permission set grants Packaging2 (profile-owned, assigned)

Verdict: org-side provisioning defect. Bypass: classic 1GP Package Manager.

The discovery that unlocked packaging — the classic Package Manager component picker names the bundle type "App Template". Probed by reading the picker's 247 options through the same-origin Visualforce iframe.

// executed in the page (classic setup iframe is same-origin):
const sel = iframe.contentDocument.querySelector('select');
[...sel.options].map(o => o.text)

// 247 component types. The ones that matter:
"App"
"App Template"      <- AppFrameworkTemplateBundle. THIS one.
"Asset File"        <- ContentAsset (the dashboard logo image)
"Analytics Visualization"
"Analytics Workspace"
...

// Neither "App Framework Template Bundle" nor "Content Asset"
// appears under its API name. The labels are the trap.
Ship the image. The dashboard names a ContentAsset; one unresolvable image fails the entire dashboard at install. It rides in the same package.

Install

Three real errors, three rules

Each installation rule below was earned by hitting the failure, reading it, and beating it. A clean customer org sees none of these; they only bite the orgs we develop in.

# the customer path is the URL; the CLI equivalent:
sf package install --package 04tjV0000000msf -o <org> --wait 10 --no-prompt

Install error #1 (verbatim) — a package cannot install into the org that built it.

$ sf package install --package 04tjV0000000msf -o tbxfarm --wait 12
Encountered errors installing the package!
1) Package(033jV0000001Y1F) Package and subscriber org namespace collision,
   Details: The installing package namespace and org namespace cannot be the same.

Rule: the publisher org is never the demo org.

Install error #2 (verbatim) — installing minutes after upload, before the version record replicates.

$ sf package install --package 04tjV0000000msf -o tbx3917 --wait 12
No record found for
SELECT AppExchangeDescription, AppExchangeLogoUrl, ... , ReleaseNotes
FROM SubscriberPackageVersion

Rule: fresh uploads take a few minutes to propagate. Retry; don't diagnose.

Install error #3 (verbatim) + fix — the target org already had the logo ContentAsset. Only bites our own dev orgs; clean customer orgs never see it.

$ sf package install --package 04tjV0000000msf -o tbx3917 --wait 10
Encountered errors installing the package!
1) Duplicate Name, Details: The name "APEX_essential_components" is already
   used on component type: Asset File. Please rename existing component.

# fix: delete the org's copy; the package restores the identical name,
# so existing dashboards re-bind automatically.
$ sf data delete record -s ContentAsset -i <03S...> -o tbx3917
$ sf package install --package 04tjV0000000msf -o tbx3917 --wait 10
install status: 0 | Status: SUCCESS

Verify

Watching a 48-node chain breathe

Ingestion is fixed-latency: ~6 minutes per stream, serial, so ten streams is about an hour, then the fast tail builds the workspace, model, vizzes and dashboard in ~2 minutes. The engine's live context (the domino runtime state) is readable mid-flight — it is where the tokens resolve from. And we know exactly what a broken org looks like, because one of ours is: the chain engine that silently dies after the first ingestion, now filed as BUG 3.

# the pulse, every few minutes:
GET /app-framework/apps/<id>?               # applicationStatus
GET /ssot/data-streams?limit=60              # lastRunStatus per stream
GET /domino/runtimes/<0ok...>/state?         # the engine's context map
